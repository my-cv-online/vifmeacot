# 05 · HTTP API and realtime protocol

The contract is `api/openapi.yaml` (OpenAPI 3.0.3). This document explains the rules that a
schema cannot express: editing semantics, locking, template locks, errors and the WebSocket
protocol. If the two disagree, fix both in the same change.

Workflow for any API change: edit `api/openapi.yaml` first → `make gen` (oapi-codegen for Go,
openapi-typescript for the web client) → implement → tests. Never edit generated files.

## 1. Conventions

| Topic | Rule |
| --- | --- |
| Base path | `/api/v1`. Health endpoints `/healthz`, `/readyz` and `/metrics` live outside it. The WebSocket is `/api/v1/ws` (§10) and is not in the OpenAPI file. |
| Format | JSON, UTF-8, `camelCase` keys. Requests that change data must send `Content-Type: application/json`. Responses over 1 KB are gzip-compressed. |
| Ids | UUID strings (UUIDv7, generated by the server). Exception: sync conflict ids are integers (`sync_changes.id`). |
| Enums | Values are the database enum values (`in_sync`, `pre_launch`, `operation_inspection`). |
| Time | Timestamps are RFC 3339 in UTC (`2026-10-08T02:15:00Z`); the UI shows them in the plant time zone from `GET /settings`. Calendar dates are `YYYY-MM-DD`. "Today" and "overdue" use the plant time zone. |
| Lists | Small master lists return `{ "items": [...] }`. Long lists (packages, findings, activity) use keyset pagination: `?limit=50&cursor=<opaque>` → `{ "items": [...], "nextCursor": "…" or null }`; `limit` max 200. |
| Versions | Every editable row has `version`. Writes send the version they are based on; a stale version gives 409 `version_conflict` (§6). |
| Request id | The client sends `X-Request-Id` (UUID) on every mutating request; the server generates one if absent, echoes it in the response header, stores it in `audit_log.request_id` and copies it into realtime events so a client can ignore the echo of its own change. |
| Language | Everything a user can read is English: error `title`/`detail`, validation and finding messages (server texts live in `backend/internal/i18n/en.go`, rule messages in the rule files). |

## 2. Errors

All errors use RFC 9457 Problem Details with `Content-Type: application/problem+json`:

```json
{
  "type": "urn:pfmea:problem:version_conflict",
  "title": "Changed by another user",
  "status": 409,
  "code": "version_conflict",
  "detail": "1 row changed since you opened it.",
  "requestId": "0192f7c4-…",
  "conflicts": [ { "entity": "failureChain", "id": "…", "currentVersion": 4, "deleted": false, "current": { "d": 5 } } ]
}
```

| `code` | HTTP | When | Extra members |
| --- | --- | --- | --- |
| `bad_request` | 400 / 415 | Malformed JSON, wrong content type, unknown query parameter value | |
| `unauthenticated` | 401 | No or expired session; wrong username or password (same message for both) | |
| `forbidden` | 403 | Role or package permission missing; `Origin` check failed | |
| `not_found` | 404 | Unknown id, or the id belongs to another package | |
| `version_conflict` | 409 | Stale `version` / `contentVersion`; row deleted by someone else | `conflicts[]` |
| `locked_by_template` | 409 | Field of a linked Template General row that the override policy does not allow (§5) | `locked[]` |
| `delete_blocked` | 409 | Delete would orphan rows (e.g. step with PFMEA rows) | `blockers[]`, `blockersTotal` |
| `release_blocked` | 409 | Template release with open Errors or without changes | `reasons[]` |
| `validation_failed` | 422 | Field validation, duplicates, business rules | `errors[]` |
| `override_reason_required` | 422 | Overridable template field changed without `overrideReason` | `errors[]` |
| `waive_not_allowed` | 422 | Waiving an Error finding | |
| `rate_limited` | 429 | Too many failed logins | `Retry-After` header |
| `internal` | 500 | Anything unexpected (logged with the request id; no stack trace in the response) | |

`errors[]` items: `{ "path": "changes[2].value", "code": "out_of_range", "message": "S must be between 1 and 10" }`.
Field error codes: `required`, `invalid_format`, `out_of_range`, `too_long`, `duplicate`,
`invalid_reference`, `not_allowed`, `not_unique_target`.

Database errors are mapped centrally, including errors raised at `COMMIT` (uniqueness of
`op_no`, `char_no` and step `seq` is checked at commit): unique violation (23505) → 422
`validation_failed` with field error `duplicate`; check violation (23514) → 422
`validation_failed`; foreign-key violation (23503, and 23001 `restrict_violation`, which
PostgreSQL raises for `ON DELETE RESTRICT`, verified in M1) → 409 `delete_blocked` on delete,
otherwise 422 `validation_failed` with field error `invalid_reference`; serialization failure (40001) and
deadlock (40P01) → retry the whole transaction up to 3 times, then 409 `version_conflict`.
Operations not implemented yet (during development) return 501 with code `internal` and title
"Not implemented yet".

When one request has several problems, the first category in this order is returned, with all
items of that category: `bad_request` → `unauthenticated` → `forbidden` → `not_found` →
`validation_failed` → `locked_by_template` → `override_reason_required` → `version_conflict`.

## 3. Authentication and permissions

- `POST /auth/login` with `{username, password}` sets the cookie `pfmea_session`
  (32 random bytes, base64url; `HttpOnly`, `SameSite=Lax`, `Path=/`, `Secure` when
  `APP_BASE_URL` is https). The database stores only `sha256(token)`. Sessions slide: expiry is
  `SESSION_TTL` (default 12 h) after the last request; `last_seen_at` is written at most every
  5 minutes. A 30-second in-memory cache avoids a database read on every request; logout and
  user deactivation evict it.
- Passwords: argon2id (m = 64 MiB, t = 3, p = 2, 16-byte salt, PHC string). Minimum 10
  characters. LDAP users (`auth_source = 'ldap'`) are created by the admin first (role is set
  in the app); login binds to the directory with the user's DN (M13).
- Failed logins: 5 per username or 20 per IP within 15 minutes → 429 `rate_limited`.
- CSRF: cookies are `SameSite=Lax`, every non-GET request must carry an `Origin` header equal to
  the origin of `APP_BASE_URL` (403 otherwise), and mutations accept only `application/json`.
- Permission checks happen in the service layer, never only in the UI. The permission matrix
  is `docs/02-phase1-scope.md` §3. In code:
  - `canEditPackage(user, pkg)`: admin or approver; or author who owns the package or is a
    member with `can_edit`. The general package uses the same rule.
  - `canRelease(user)`, `canWaive(user)`: admin or approver.
  - Master data, users, rules and settings: admin. Everyone authenticated may read them.
- `GET /packages/{id}` returns `permissions` (`canEdit`, `canRelease`, `canWaive`,
  `canManageMembers`) so the UI can hide controls; the API still enforces them.

## 5. Template locks and overrides

Rows in a model package with `origin = general` are linked copies of Template General rows
(`docs/07-template-general.md`). Editing rules, evaluated per field:

1. The package is the general package → editable (it is the template's working copy).
2. `origin = local` or `syncStatus = detached` → editable.
3. `syncStatus = review` (template deleted the source row) → 409 `locked_by_template` until the
   conflict is resolved.
4. `syncStatus` is `in_sync` or `override`:
   - the field is in the override policy → editable **with** `overrideReason`
     (≥ 3 characters; optional when the field is already overridden, then the old reason
     stays). The server stores `overrides[column] = {reason, by, at, templateValue}` where
     `templateValue` is the value in the synced template revision, and sets
     `syncStatus = override`;
   - otherwise → 409 `locked_by_template`.
5. Virtual fields follow their target: `failureMode.effectS` follows `failureEffect.s`,
   `failureChain.pcText`/`dcText` follow `control.text`.
6. Deleting a linked row: only whole optional general steps may be removed (with their linked
   children, and only if no local rows hang below them). Everything else must be detached
   first (`/linked-rows/detach`).
7. Reordering (`/move`) is always allowed on linked rows: `seq` is local and never synced.

The policy lives on the general package (`packages.override_policy`, table → columns). The API
exposes it with entity and field names, for example:

```json
{ "failureEffect": ["s"], "cpLine": ["sampleSize", "sampleFreq"], "reactionPlan": ["text"] }
```

The policy may only name fields that are sync columns (`docs/07-template-general.md` §1) and
editable in Phase 1 (§4). Every view returns it once as `templatePolicy`; the client derives the lock state of each cell
(`locked`, `overridable`, `overridden`) from the row's `origin`, `syncStatus`, `overrides` and
this policy. Fields that never sync (`seq`, ids, link columns) are not part of the policy.

Overrides in API payloads use field names as keys:
`"overrides": { "sampleFreq": { "reason": "…", "by": "…", "at": "…", "templateValue": "Every lot" } }`.

## 6. Editing cells: `POST /packages/{packageId}/changes`

The grids and header forms save through one endpoint. A request is one user gesture: a cell
edit, a fill-down, a multi-cell paste inside existing rows.

```json
{
  "changes": [
    { "entity": "failureChain", "id": "…", "field": "d", "value": 6, "version": 3 },
    { "entity": "cpLine", "id": "…", "field": "sampleFreq", "value": "Every reel", "version": 5,
      "overrideReason": "Agreed with Customer B" }
  ]
}
```

### 6.1 Semantics

1. Maximum 500 changes per request; the client splits a larger gesture (for example a big
   multi-cell paste into existing rows) into several requests, each all or nothing.
2. All or nothing: one database transaction; any error rolls back everything. The transaction
   first locks the package row (`SELECT 1 FROM packages WHERE id = $pkg FOR NO KEY UPDATE`).
   Every transaction that writes package content does this (creates, deletes, paste, link
   operations, sync jobs, release, restore; the sync job locks its `package_links` row just
   before it): it serialises writes per package and removes deadlocks on the
   `content_version` counter that the triggers update.
3. Changes are grouped by row (`entity`, `id`). All changes for one row must carry the same
   `version` (otherwise 422). Each row is updated with one statement:
   `UPDATE … SET … WHERE id = $id AND package_id = $pkg AND version = $version`.
4. Zero rows updated → the row is stale or deleted → 409 `version_conflict` listing every
   stale row with `currentVersion` and `current` values (or `"deleted": true`). No partial
   success.
5. Validation (§4), permissions (§3) and template locks (§5) are checked before any write;
   all problems of the request are reported together.
6. After the update the transaction publishes realtime events (§10) and commits. Triggers
   maintain `s`, `rpn`, `newRpn`, `version`, `updated_at`, `content_version` and the audit log.
7. After commit the rule scheduler is notified with the touched tables; findings arrive later
   through the `findings.changed` event (`docs/06-rules.md` §3). The response never waits for
   rules.

### 6.2 Response

```json
{
  "performed": true,
  "contentVersion": 1843,
  "rows": [
    { "entity": "failureEffect", "id": "…", "op": "update", "version": 4, "derived": false, "values": { "s": 8 } },
    { "entity": "failureChain", "id": "…", "op": "update", "version": 7, "derived": true, "values": { "s": 8, "rpn": 128 } }
  ],
  "deleted": [], "unlinked": [], "skipped": []
}
```

Every content mutation (creates, deletes, moves, link operations) returns this
`MutationResult`; `deleted` / `unlinked` count rows removed or unlinked by cascades, `skipped`
lists inputs that were ignored with a reason, and `performed` is false for `dryRun`.

`rows` contains every row whose stored values changed: the edited rows (`values` = edited
fields plus their read-only dependants such as `rpn`, `newRpn`, `completedOn`, link fields) and
`derived: true` rows changed by triggers (other chains after an effect S change). Virtual
fields may also produce `op: "insert"` or `op: "delete"` rows (§6.4).

### 6.3 Conflicts and client rebase

On 409 the grid does not overwrite silently. For each conflicted row it compares the server's
`current` value of the field the user edited with the value the user started from:

- same value (someone changed *another* field) → re-send the change with `currentVersion`
  once, automatically;
- different value → show the conflict prompt with "Keep my value" (re-send with the new
  version) and "Use server value" (discard).

This gives field-level merging while the server keeps a simple row version.

### 6.4 Virtual fields

They let the flat AIAG 4th grid edit one-to-many data in one cell:

| Virtual field | Target | Behaviour |
| --- | --- | --- |
| `failureMode.effectText`, `failureMode.effectS` | the failure mode's only `failureEffect` | 0 effects → insert one (`level = unspecified`); 1 effect → update it; ≥ 2 effects → 422 `validation_failed` with field error `not_unique_target` (the UI then opens the effect list editor). |
| `failureChain.pcText`, `failureChain.dcText` | the chain's only prevention / detection `control` | 0 → insert (empty value: no-op); 1 → update, or delete when the value is empty; ≥ 2 → 422 with field error `not_unique_target`. |

The `version` sent with a virtual field is the version of the owning row (failure mode or
chain). When the target row exists, the client also sends its version as `targetVersion` (the
view returns effect and control versions). The server locks the target with
`SELECT … FOR UPDATE` and answers 409 `version_conflict` when the target's version differs,
when a target exists but no `targetVersion` was sent (someone created it meanwhile), or when
`targetVersion` was sent but the target is gone. Two users editing the same Sev or control
cell therefore never overwrite each other silently.

## 7. Structural operations

| Operation | Endpoint | Notes |
| --- | --- | --- |
| Create a row | `POST /packages/{id}/steps`, `/step-flows`, `/characteristics`, `/pfmea-rows`, `/failure-effects`, `/controls`, `/actions`, `/cp-lines` | Returns the created rows in the same `rows` format as `/changes`. `charNo` is generated (`<opNo>-<next 2 digits>`) when omitted. A new step is placed after `afterStepId` (or at the end). |
| Create a full PFMEA row | `POST /packages/{id}/pfmea-rows` | Creates failure mode (or reuses `failureModeId`), optional single effect, cause, chain and optional prevention/detection controls in one transaction. |
| CP lines from PFMEA | `POST /packages/{id}/cp-lines/from-pfmea` | One line per selected control: step and characteristic from the control's failure mode, `controlId` and `failureModeId` set, `evalTechnique` = control text (detection) or `controlMethod` = control text (prevention), `isErrorProofing` from the library item; an empty reaction plan row is created. Controls that already have a line in that phase are skipped and reported. |
| Delete | `DELETE /packages/{id}/<collection>/{rowId}?version=N` | `?dryRun=true` returns what would be deleted or unlinked without deleting. Blocked deletes return 409 `delete_blocked` with up to 50 `blockers` (`entity`, `id`, `label`). |
| Reorder | `POST /packages/{id}/move` `{entity, id, version, afterId}` | Renumbers `seq` of the siblings (10, 20, 30 …) in one transaction. Sibling scope: steps per package; characteristics and failure modes per step; effects, causes and chains per failure mode; controls per chain and kind; actions per chain; CP lines per phase and step. |
| Bulk paste | `POST /packages/{id}/paste` | §8. |

Delete rules (the database enforces the same with `ON DELETE RESTRICT`):

- step: blocked while failure modes or CP lines reference the step or its characteristics; its
  characteristics and flows are deleted with it;
- characteristic: blocked while failure modes or CP lines reference it;
- failure chain: deletes its cause, controls and actions; deleting the last chain of a failure
  mode also deletes the failure mode and its effects (CP lines that referenced the failure mode
  keep the line and lose the link, which R03 then reports);
- failure mode: deletes effects, causes, chains, controls, actions;
- control: CP lines keep the line and lose the link;
- CP line: deletes its reaction plan.

## 8. Bulk paste from Excel: `POST /packages/{packageId}/paste`

```json
{
  "target": "pfmeaRows",
  "columns": ["opNo", "stepName", "charNo", "requirement", "failureMode", "effect", "s", "class",
              "cause", "prevention", "o", "detection", "d", "recommendedAction", "responsible", "targetDate"],
  "rows": [["30", "Solder paste printing", "30-01", "Solder paste volume", "Insufficient paste", "…", "7", "SC", "…", "…", "4", "…", "4", "", "", ""]],
  "fillDown": true,
  "dryRun": true
}
```

- `target`: `pfdSteps`, `pfmeaRows` or `cpLines` (with `phase`). Allowed column keys
  (`PasteColumn`; `ignore` is always allowed):
  - `pfdSteps`: `opNo`, `stepName`, `function`, `symbol`, `machines`, `department`, `wiRef`,
    `charNo`, `charKind`, `requirement`, `spec`, `class`;
  - `pfmeaRows`: `opNo`, `stepName`, `function`, `charNo`, `requirement`, `class`,
    `failureMode`, `effect`, `s`, `cause`, `prevention`, `o`, `detection`, `d`,
    `recommendedAction`, `responsible`, `targetDate`;
  - `cpLines`: `opNo`, `stepName`, `machines`, `charNo`, `charKind`, `requirement`, `class`,
    `spec`, `evalTechnique`, `gauge`, `sampleSize`, `sampleFreq`, `controlMethod`,
    `reactionPlan`.
  A key outside the target's list or used twice makes the request malformed → 422
  `validation_failed`.
- `fillDown` (default true) copies the value from the row above into empty cells of the
  hierarchical columns (`opNo`, `stepName`, `charNo`, `requirement`, `failureMode`, `effect`,
  `s`, `class`), because Excel copies merged cells as one value plus empty cells.
- Matching, never updating: steps by `opNo`, characteristics by `charNo` (or by step + name),
  failure modes by step + characteristic + text, effects by failure mode + text, controls by
  chain + kind + text. Matched rows are reused; differences to existing values are reported as
  warnings, never written. Linked general rows can receive local children.
- `class` is matched against `sc_symbols.code` and the customer's printed symbols.
- For a well-formed request the response is always 200 `PasteResult` (`valid`, `performed`, `rowsTotal`, `errors[]`,
  `warnings[]`, `creates{entity: n}`, `matches{entity: n}`, `contentVersion`). `dryRun: true`
  only validates. `dryRun: false` creates everything in one transaction when the input is
  valid; otherwise nothing is created and `performed` is false.
- Maximum 2,000 rows per request.

## 9. Reads

- **Views** (one request per screen, built by a single SQL statement with `json_agg`, streamed
  to the client as bytes; `docs/03-architecture.md` §4):
  `GET /packages/{id}/views/pfd` → `PfdView`, `/views/pfmea` → `PfmeaView`,
  `/views/control-plan?phase=production` → `ControlPlanView`. Views are normalized (one array
  per entity) and carry `contentVersion` and `templatePolicy`.
- **Package lists** use `package_stats` for counters; no per-row subqueries.
- **Search** `GET /search?q=` (≥ 2 characters) uses the `pg_trgm` indexes and returns up to 10
  packages, steps and characteristics each.
- **Long-running work** returns 202 with a resource to watch: template release → `SyncRun`
  (`GET /sync-runs/{id}`, event `sync.progress`); export → `ExportFile` (`GET /exports/{id}`,
  event `export.ready`). A cached export returns 200 immediately.
- **Checks**: `POST /packages/{id}/checks` runs a full check and returns the `CheckRun` (target
  < 2 s). Findings: `GET /packages/{id}/findings` (includes `lastCheckRun`) and the
  cross-package `GET /findings`. Waive and unwaive refresh `package_stats` and publish
  `findings.changed` in the same transaction, so counters never wait for the next check.

## 10. Realtime: WebSocket `/api/v1/ws`

One connection per browser tab, authenticated by the session cookie; the `Origin` header is
checked on upgrade. Messages are JSON text frames with a `type` field. Library:
`github.com/coder/websocket`.

Client → server:

| Type | Payload | Purpose |
| --- | --- | --- |
| `subscribe` | `{packageId}` | Receive events of a package (max 5 per connection). Requires read access. |
| `unsubscribe` | `{packageId}` | |
| `focus` | `{packageId, entity, id, field}` or `{packageId}` to clear | Presence: which cell the user is in. Client throttles to 2 per second. |
| `ping` | `{}` | Keep-alive every 25 s; the server closes connections silent for 60 s. |

Server → client:

| Type | Payload |
| --- | --- |
| `hello` | `{userId, serverTime, protocol: 1}` |
| `rows.changed` | `{packageId, contentVersion, requestId, by: {id, displayName}, rows: [ChangedRow]}` (same row format as §6.2) |
| `rows.created` | same as `rows.changed` with `op: "insert"` rows (full row objects in `values`) |
| `rows.deleted` | `{packageId, contentVersion, requestId, by, rows: [{entity, id}]}` |
| `package.reload` | `{packageId, contentVersion, reason}`: refetch the open view (`reason`: `template_sync`, `restore`, `paste`, `too_large`) |
| `findings.changed` | `{packageId, checkRunId, opened: [Finding], fixed: [findingId], updated: [Finding], counts: {errorsOpen, warningsOpen, infosOpen, waived}}`; `checkRunId` is null and only `updated` is filled for a waive or unwaive; the lists are omitted with `"reload": true` when too large |
| `presence` | `{packageId, users: [{id, displayName, focus?}]}` (debounced 250 ms) |
| `sync.progress` | `{syncRunId, status, packagesTotal, packagesDone, packagesFailed}` (sent to all connections) |
| `export.ready` | `{exportId, packageId, status}` (sent to the requesting user only) |
| `pong` | `{}` |

Delivery path: the code that writes data calls `pg_notify('pfmea_events', payload)` **inside
the same transaction**, so events are delivered only after commit. One dedicated connection
`LISTEN`s and the in-memory hub fans out to subscribers. Payloads larger than 7,900 bytes are
replaced by `package.reload` (or `findings.changed` with `reload: true`). Clients ignore
events whose `requestId` they sent themselves. After a reconnect the client compares
`contentVersion` and refetches the view if it moved.

Presence lives only in memory (single application instance in Phase 1).
