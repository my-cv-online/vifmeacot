# 06 · Consistency rules and the rule engine

The rule catalog (42 rules, English titles) is seeded by the migration into `rules`. Phase 1
implements the 32 rules with `phase = 1`; each is one SQL file in
`backend/internal/rules/sql/<CODE>.sql` with a fixture in
`backend/internal/rules/testdata/<CODE>.sql`. All 32 files already exist and pass against
`db/seed/demo.sql`. Do not rewrite them; extend them only when a fixture proves a gap.

## 1. Rule file contract

```sql
-- rule: R04
-- reads: failure_chains, controls, control_library
-- message: D = {{.d}} (step {{.opNo}}) is too low for method {{.methods}}; the control library requires D of at least {{.dMin}}.
-- returns: object_type, object_id, field, key, params (lihat docs/06-rules.md)
SELECT 'failure_chains'::text, ch.id, 'd'::text, ''::text,
       jsonb_build_object('d', ch.d, 'opNo', s.op_no, 'dMin', x.d_min, 'methods', x.methods)
FROM failure_chains ch …
WHERE ch.package_id = @package_id …
```

| Part | Rule |
| --- | --- |
| `-- rule:` | Code; must exist in `rules` with `phase = 1`. The loader fails at startup otherwise. |
| `-- reads:` | Tables whose changes can change the result. Drives incremental checks. `all content tables` means every content table. Tables used only for message text may be omitted. |
| `-- message:` | Go `text/template`, English (it is shown in the UI), one line. Variables come from `params`. Parse with `Option("missingkey=error")`. Other comment lines in rule files are Indonesian. |
| Parameters | `@package_id` (uuid) and `@today` (date in the plant time zone). Run with `pgx.NamedArgs`. |
| Columns (by position) | `object_type` text (table name), `object_id` uuid, `field` text (API field name in camelCase, `''` = whole row), `key` text (disambiguates several findings on the same object and field, `''` if not needed), `params` jsonb (camelCase keys). |
| Must | Filter by `@package_id`; be read-only and deterministic; use indexed joins; never read `findings`; return API field names (use `snake_to_camel()` when the name comes from data, as T03 does). |

Pseudo-fields used as deep-link targets (no column of that name exists): `failureMode.effects`
(F01, the effects cell), `package.steps` (T01), `package.templateRev` (T02),
`processStep.ngFlow` (W02, the flow panel), `package.lastReviewedAt` (W04),
`cpLine.reactionPlan` and `cpLine.spec` (C01, shown in the CP row).

## 2. Engine (`backend/internal/rules`)

1. **Load** at startup from `embed.FS`: parse the header lines, compile the message template,
   verify the code in the `rules` table. Keep a map `table → []rule` from `reads`.
2. **Effective configuration per package**: a rule runs when `rules.is_enabled` and the
   customer override (`rule_overrides.is_enabled`, NULL = default) allow it and the rule's
   `applies_to` matches the package (`all`, or equal to `pfmea_method` / `cp_format`). Level =
   `coalesce(rule_overrides.level, rules.default_level)`.
3. **Execute** in one consistent snapshot. The engine has its own pgx pool (`RULE_POOL_SIZE`,
   default 8) so checks never starve API requests. At most
   `RULE_POOL_SIZE / RULE_PARALLELISM` checks run at once (a semaphore), and a check acquires
   all of its `RULE_PARALLELISM` connections (default 4) only after it holds the semaphore, so
   checks can never wait on each other for connections.
   - First connection: `BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY`, then
     `SELECT set_config('TimeZone', $1, true), set_config('jit', 'off', true)` with the plant
     time zone (W04 formats and compares timestamps), then `SELECT pg_export_snapshot()`.
   - Other connections: `BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY`, then
     `SET TRANSACTION SNAPSHOT '<id>'` **before any query**, then the same `set_config` call.
     The snapshot id is generated by the server; validate it with
     `^[0-9A-F]+-[0-9A-F]+(-[0-9]+)?$` before placing it in the statement (it cannot be a
     parameter).
   With parallelism 1 all rules run in the first transaction (used by tests).
4. **Fingerprint** each result: `sha256(rule_code | object_type | object_id | field | key)` as
   hex. Render the message.
5. **Write** in one transaction protected by `pg_advisory_xact_lock(hashtextextended('check:' || package_id::text, 0))`:
   - upsert every result (`INSERT … ON CONFLICT (package_id, fingerprint) DO UPDATE`):
     update `level`, `message`, `params`, `last_seen_at`; a `fixed` finding becomes `open`
     again (`fixed_at = NULL`); a `waived` finding stays waived **unless** its level is now
     `error`, then it becomes `open` (Errors can never be waived);
   - every `open` or `waived` finding of the executed rules that was not seen becomes
     `fixed` (`fixed_at = now()`);
   - a full check deletes `open` findings of rules that are disabled for this package;
   - insert the `check_runs` row (trigger, rule codes, duration, opened, fixed, still open);
   - refresh `package_stats` with one `INSERT … ON CONFLICT DO UPDATE` statement;
   - `pg_notify('pfmea_events', …)` with `findings.changed` (`docs/05-api.md` §10).
6. **Errors**: a failing rule is logged with its code, recorded in `check_runs.error`, and
   the other rules still count; findings of the failed rule are left untouched.
7. **Waive / unwaive** change a finding's status outside a check. The transaction takes the
   same `pg_advisory_xact_lock` as step 5 (so a running check cannot overwrite the counters),
   refreshes `package_stats` and publishes `findings.changed` with the finding in `updated`
   (`docs/05-api.md` §9–10).

### Fixed vs. disappeared objects

When an object is deleted its findings are no longer returned and become `fixed`. That is
intended: the problem is gone.

### Location of a finding

The API adds `location` (`docType`, `stepId`, `opNo`, `phase`) to every finding, and the
`docType` filter uses it. The findings list query derives it with one `LEFT JOIN` path per
object type; objects that no longer exist give a null location.

| `object_type` | `docType` | Step | Phase |
| --- | --- | --- | --- |
| `process_steps` | PFD | the step | — |
| `step_flows` | PFD | `from_step_id` | — |
| `characteristics` | PFD | `step_id` | — |
| `failure_modes` | PFMEA | `step_id` | — |
| `failure_effects`, `failure_causes`, `failure_chains` | PFMEA | step of the failure mode | — |
| `controls`, `actions` | PFMEA | step of the chain's failure mode | — |
| `cp_lines` | CP | `step_id` | the line's `phase` |
| `reaction_plans` | CP | step of the CP line | phase of the CP line |
| `documents` | the document's `doc_type` | — | `header.phase` for CP |
| `packages` | — (package level) | — | — |

## 3. When checks run

| Trigger | `check_trigger` | Scope | Mechanism |
| --- | --- | --- | --- |
| Save (`/changes`, create, delete, move, paste, link operations) | `save` | Rules whose `reads` intersect the touched tables | In-process scheduler, coalesced per package: changes arriving while a check runs are merged into one follow-up run; a 150 ms debounce batches fast typing. Concurrency is bounded by the rule pool (`RULE_POOL_SIZE`). |
| "Run check" (`POST /packages/{id}/checks`) | `manual` | All enabled rules | Synchronous; waits for a running check of the same package first. |
| Template sync of a package, package creation | `sync` | All | After the sync transaction commits. |
| Master data change (customer CSR settings, symbol table, parts, control library, banned terms, rules, rule overrides, settings) | `manual` | All, for the affected packages (customer's packages, packages using the part, or all) | River job `check_packages`. |
| Nightly at `nightly_check_time` (plant time) | `nightly` | All, every package | River periodic job; needed because F11 and W04 depend on `@today`. |
| Application start | `nightly` | All, for packages without a `package_stats` row or with `packages.updated_at > package_stats.last_check_at` | Catches checks lost by a restart. |
| `pfmea seed-demo` (from M8) | `manual` | All, every package | Gives the demo data its findings (E2E tests start from them). |

Targets (3,000-chain package): incremental check < 300 ms, full check < 2 s.

## 4. Phase 1 rules

Level: E = Error (blocks approval from Phase 2), W = Warning (needs justification or waiver),
I = Info. The English titles shown in the UI are in the `rules` table.

- The general package has no customer, part or template link, so S02, S04, F08, K06 and
  T01–T04 never fire there.
- R01/R02 accept "the same control text" because one CP line often implements one control that
  appears on several chains.

owner and content, volume-based frequency, Safe Launch exit criteria, SC detection only visual),

## 7. Fixtures

Each fixture is SQL applied on top of the demo seed inside a transaction that is rolled back:

```sql
-- fixture: K01 on top of db/seed/demo.sql, package PS-07, @today = 2026-10-08
-- scenario: A new step without failure modes is reported.
-- expect: [{"object_type": "process_steps", "field": "name", "params": {"opNo": "95"}}]
INSERT INTO process_steps (package_id, op_no, seq, name, symbol)
VALUES ((SELECT id FROM packages WHERE code = 'PS-07'), '95', 95, 'Conformal coating', 'operation');
```

`expect` is the **complete** output of that rule for PS-07 after the fixture (baseline findings
included). Matching is a multiset match: same count, and every expected item matches one result
with equal `object_type` and `field` and `params` containing the expected keys and values.

Each fixture is listed as a test case in `docs/test-cases/rules.md` (`TC-RULE-<CODE>-<n>`), and
the Go subtests are named after those IDs (`TestRuleFixtures/TC-RULE-K01-1`,
`TestBaseline/TC-RULE-BASE-1`). The Go test (`backend/internal/rules/rules_test.go`,
`make test-rules`) does, per fixture:
start PostgreSQL 18 (testcontainers, or `TEST_DATABASE_URL`), migrate, load the seed once,
then `BEGIN` → fixture SQL → run the rule with `@package_id` = PS-07 and `@today` =
2026-10-08 → compare → `ROLLBACK`. A second test runs all rules on PS-07 and GENERAL and
compares with §5.

## 8. Adding or changing a rule

Use the `/add-rule` skill. In short: write the fixture first (`expect` must fail), write or
change the SQL, run `make test-rules`, keep §5 true, update §4 and the `rules` seed (new
migration) if the catalog changes.
